# ADR — Doctor resolves through the SAME project-root + alias map codegen trusts; the unresolved-on-build condition becomes a doctor finding

## Context
- 0019 unified the two CODEGEN module loaders behind `resolve_module_plugins` and added `find_project_root` (an UPWARD walk to the nearest `Lazurite.toml`) so `lazuli generate go app` resolves the repo-root `[plugins]` block. 0019 explicitly scoped doctor OUT ("Unifying doctor's separate alias map with the codegen resolver — that's 0020").
- Doctor builds its OWN resolution view. `crates/lazuli_doctor_run/src/doctor/aggregators/lazurite_manifest/plugins_semantic.rs` calls `build_alias_map(Some(manifest), &package.project_root)` in three places (`check_semantic_plugin_unresolved` :107-110, `check_semantic_plugin_no_validator` :42-48, `check_plugin_unused` :242-243). It uses the SAME `build_alias_map` function as codegen — but feeds it `package.project_root`, which comes from `doctor_project_root` (`helpers.rs:226-235`): a directory input passes through UNCHANGED, with NO upward walk.
- So the two surfaces diverge on the ROOT, not the function. `lazuli doctor app` → root = `app/` → `Lazurite.toml` not found there → either the whole `lazurite_manifest_diagnostics` aggregator short-circuits to empty (`mod.rs:40-42`, `project_has_lazurite_manifest` false) and doctor goes SILENT, or (manifest at `app/`) an empty/partial alias map false-flags `SEMANTIC-PLUGIN-001`. Meanwhile `generate go app` walks UP, finds the repo-root manifest, and resolves. **Doctor-green ≠ codegen-green.**
- Dependency reality: `lazuli_doctor_run` depends on `lazuli_manifest` but NOT on `lazuli_cli`. 0019's `find_project_root` lives in `lazuli_cli/src/module_loader/plugin_resolution.rs` — unreachable from doctor. The shared root-walk therefore cannot stay in `lazuli_cli` if doctor is to call the identical code.
- The bridge reality (verified): the `lazuli_diagnostics_registry` bridge test scans only `crates/lazuli_doctor/src/**` for `const …CODE…: &'static str` consts. The plugin-semantic checks live in `lazuli_doctor_run` and use INLINE string literals (`code: "SEMANTIC-PLUGIN-001".to_owned()`), so they are NOT currently scanned. Extending an existing inline-literal code stays invisible to the bridge; introducing a NEW `CODE` const in `lazuli_doctor/src` WOULD require a `lazuli_keywords` claim.

## Decision
- **One project-root rule, shared.** Re-home the upward `Lazurite.toml` walk into `lazuli_manifest` (`lazurite_manifest::find_project_root(input) -> Option<PathBuf>`), the crate BOTH `lazuli_cli` and `lazuli_doctor_run` already depend on. 0019's `find_project_root` becomes a thin re-export (or delegates) so codegen behavior is byte-identical; doctor's package loader calls the SAME function. There is now ONE upward-walk used by check + doctor + every generate path. `doctor_project_root` stays for the legacy no-manifest single-file case, but the plugin-semantic path uses the shared walk.
- **One alias map, shared inputs.** Doctor keeps calling `build_alias_map(Some(manifest), &root)` — but `root` is the shared `find_project_root` result and `manifest` is loaded from THAT root, so the alias map doctor builds is byte-identical to the one codegen builds. The duplicate, root-divergent map is eliminated by construction: same function, same root, same manifest ⇒ same map.
- **The unresolved-on-build condition becomes a doctor finding.** Surface the SAME residual condition 0019's loud scan uses — `[plugins]` present AND a `@semantic.<X>` reference with no resolving alias on the authoritative root — as a doctor finding at the field site. Implement by **extending `SEMANTIC-PLUGIN-001`** (not a new code): it already covers "`@semantic.<X>` resolves to neither built-in nor any active plugin alias" — the residual condition is exactly that, now evaluated over the AUTHORITATIVE root instead of the divergent one. Re-pointing the root makes the existing rule fire correctly; no new code, no bridge churn. The fix is a root swap inside the existing inline-literal check.
- **Give the unification its own auditable home.** Move the three plugin-semantic checks' shared "resolve the authoritative alias map for this package" step into ONE helper (`authoritative_alias_map(package) -> Result<AliasMap, _>`) in a new module `aggregators/lazurite_manifest/plugin_resolution_view.rs` with a `//!` trigger-cue header (fires-when phrasing) for the module_headers meta-lint. All three call sites consume that single helper, so they can never again diverge on root. This is a `lazuli_doctor_run` module with NO new `CODE` const (it reuses `SEMANTIC-PLUGIN-001`), so the bridge stays untouched — but if a NEW code is judged necessary during build, it lands in `lazuli_doctor/src` with a matching `GLOBAL_DIAGNOSTICS` claim.

## Alternatives considered
- **Add a brand-new `SEMANTIC-PLUGIN-RESOLVE-DRIFT-001` code** — rejected: the condition is identical to `SEMANTIC-PLUGIN-001` ("this `@semantic.*` doesn't resolve"); a second code splits one concept and forces a `lazuli_keywords` GLOBAL claim + bridge wiring for no semantic gain. Re-point the existing rule's root instead. (Kept as a fallback ONLY if the build discovers a case the existing code genuinely cannot express; then it's a GLOBAL_DIAGNOSTICS entry in `lazuli_doctor/src`.)
- **Make doctor import `resolve_module_plugins` from `lazuli_cli` and run the full IR resolution, then inspect residuals** — rejected: forces a `lazuli_doctor_run → lazuli_cli` dependency (a layering inversion; doctor is a leaf the CLI composes), and doctor doesn't need the rewritten IR, only the alias map + the reference set it already collects from text. Sharing the ROOT + the `build_alias_map` call is the minimal seam closure.
- **Make codegen consume doctor's view instead** — rejected (and the inverse of 0019): codegen must resolve standalone (`generate` runs without doctor); doctor is the redundant copy, so doctor adopts codegen's authoritative root.
- **Leave `doctor_project_root` as-is and just special-case plugins** — rejected: a third root rule is exactly the drift this spec kills. One walk, shared.

## Consequences
**We accept:** moving `find_project_root` down to `lazuli_manifest` (a small, mechanical relocation; 0019's call site becomes a re-export so its tests stay green) and threading the shared root through doctor's plugin-semantic helper. The residual finding may surface on a project that was previously false-clean (doctor silent because root was misdetected) — that is the bug being fixed; the finding is correct.
**We gain:** `lazuli doctor` becomes a true precondition for `generate` — doctor-green ⇒ the generate path resolves identically; the duplicate text-based map dies; the two surfaces can never drift on root again; every later Plugin Platform spec (0021-0023) checks and builds through one resolution. hostpoint `lazuli doctor app` and `lazuli generate go app` agree on the BR scalars.
**We watch:** if the residual finding ever fires where `generate` actually resolves (or stays silent where `generate` fails), the root or the alias map is STILL diverging — the agreement test is the tripwire; tighten the shared seam, never let the two re-fork. And if a third consumer of plugin resolution appears, it MUST call the shared `find_project_root` + `build_alias_map`, enforced by the agreement test pattern.
