# ADR — `lazuli plugin verify` walks the real resolver per plugin; a doctor check makes the declared adapter contract fail at compile time; method-set conformance stays the runtime assertion's job

## Context
- After 0019/0020/0021 the machinery is sound but **unproven per project**. 0019 unified resolution into one mandatory pipeline; 0020 made doctor + codegen share ONE authoritative resolver; 0021 turned `manifest.toml` into a typed multi-kind shape so `implements` / `[binds]` / `[env]` are parsed fields. Nothing yet asserts the FULL chain holds for a given app's `[plugins]`.
- The adapter dimension is the sharp edge. Today adapter binding is **runtime-only string lookup**: a plugin's Go `init()` calls `lazuli.RegisterAdapter("@lazuli/plugin-mercadopago", newAdapter())`, the facade does `LookupAdapter(ref)` at request time, and the ONLY static artefact is the side-effect import. `crates/lazuli_cli/src/lazurite_codegen.rs` reads `[plugins]`, resolves each plugin's `go_module` (from `go.mod` for local plugins) and packs a `LazuritePlugin`; `crates/lazuli_codegen_go/src/emitter/root/main_go.rs:273-308` emits `_ "<go_module>"` per plugin so its `init()` lands in the binary's import graph. That is the whole compile-time story — there is NO check that `implements`'s named interface exists, nor that the app actually binds the capability to this plugin.
- The plugin's own `adapter.go` already carries the method-set proof: `var _ payments.PaymentGateway = (*Adapter)(nil)` (a Go compile-time assertion). That assertion fires under `go build`/`go test`, which the Rust compiler cannot and should not invoke.
- The runtime bucket interfaces are a known, closed set living at `runtime/go/lazuli/{payments,storage,maps,notifications,auth}/` (`payments.PaymentGateway`, `storage.ObjectStore`, `maps.Geocoder`, `notifications.EmailSender`, `auth/social.Provider`, …). They are enumerable from Rust without compiling Go.
- hostpoint declares 8 active plugins with heterogeneous legacy interface fields (`implements` scalar / `[binds].interface` / `[provides].go_interface`); 0021 normalises these. The verify/contract layer reads the NORMALISED typed fields.

## Decision
1. **`lazuli plugin verify` walks the real resolver, one plugin at a time, and reports per-link.** It is NOT a re-implementation of resolution — it loads the project via the same authoritative path codegen uses (0020's shared resolver + 0021's typed manifest loader) and inspects the resulting state. For each declared plugin it checks an ordered link chain and stops reporting deeper links once an earlier one breaks (a missing manifest makes "alias resolves" meaningless):
   - **L1 manifest** — `manifest.toml` found at the resolved plugin root and parsed into the typed 0021 shape (no parse error, has a `[plugin]` block).
   - **L2 semantic** — every `@semantic.*` the plugin declares resolves through the authoritative alias map (skipped/`n/a` for adapter-only plugins).
   - **L3 contract** — if the plugin declares `implements` / `[binds]`: the interface name is a KNOWN bucket interface AND (where the app expresses a registry binding) the capability binds to THIS plugin's ref. (`n/a` for semantic-only plugins.)
   - **L4 import** — `go_module` resolves (from `go.mod` for local plugins, per `read_plugin_go_module`) AND the side-effect import for it WILL be emitted by the main.go emitter (i.e. the plugin survives into `LazuritePlugin { go_module: Some(_) }`).
   - **L5 env** — every var in the manifest's required `[env]` set is present in the app's env contract (declared env / `.env` keys the app surfaces).
   Exit code is non-zero if ANY plugin has ANY FAIL. `--plugin <ns>` scopes to one plugin. Output is human (a per-plugin table of links with the broken one called out + its fix) and `--json` (a structured `{ plugin, links: [{ id, status, detail }], overall }[]`). Both carry the honest-limit note that L3 verifies the DECLARED contract, not Go method-set conformance.
2. **A doctor check `PLUGIN-CONTRACT-001` makes the adapter contract fail at compile time.** It lives as a `lazuli_doctor` rule (co-located `pub const CODE`, `//!` trigger-cue header) so it flows through `lazuli check` / the LSP / CI like every other diagnostic, and it is bridged into the run aggregator (`lazuli_doctor_run`'s `lazurite_manifest` cluster, next to `PLUGIN-MANIFEST-MISSING` / `SEMANTIC-PLUGIN-001`). It fires, at **error** severity, when an adapter plugin is declared and EITHER:
   - its `implements` / `[binds].interface` names an interface that is NOT in the known bucket-interface catalog (typo / nonexistent bucket), OR
   - it declares a capability via `implements` but the app's registry has NO binding pointing the capability at this plugin's ref (declared adapter, unbound capability).
   The message names the plugin, the offending interface/capability, the closest known bucket (when it's a near-miss), and the fix. The check is registered in `lazuli_keywords` facets (a new `P_PLUGIN_CONTRACT` facet group carrying `df("PLUGIN-CONTRACT-001", "error", "correctness")`) so the `lazuli_diagnostics_registry` bridge test stays green.
3. **The known-bucket-interface catalog is a Rust-side closed list mirroring `runtime/go/lazuli/`.** v1 enumerates the shipped buckets (`payments.PaymentGateway`, `storage.ObjectStore`, `maps.Geocoder`, `notifications.EmailSender`, `auth/social.Provider`) as a `const &[&str]` in the contract-check module, exactly as `check_semantic_plugin_unresolved` hard-codes `BUILT_IN_SEMANTIC`. A pre-`[plugin]`/pre-typed-fields manifest (one 0021 hasn't normalised, or that genuinely declares no interface — e.g. sms-twilio's bare `[provides]`) contributes NO contract link and is `n/a`, never a false FAIL.
4. **Honest static boundary, stated three times.** `verify`'s L3 line, the `PLUGIN-CONTRACT-001` message tail, and `docs/plugin-authoring.md` all state: "This verifies the DECLARED contract + wiring graph. Whether the Go `Adapter` type actually satisfies the interface's method set is proven by the runtime `var _ <Interface> = (*Adapter)(nil)` assertion under `go build` / `go test` — keep it in your `adapter.go`." We never pretend Rust verified the method set.

## Alternatives considered
- **Shell out to `go build` from `verify`** to get true method-set verification — rejected: makes the Rust compiler depend on a Go toolchain + the plugin's full module graph being fetchable, turns a fast static check into a slow networked one, and duplicates what the plugin's own `var _ Interface = (*Adapter)(nil)` + its `go test` already do. The static/runtime split is honest and fast; the Go assertion is the right home for method-set proof.
- **Make `verify` a thin wrapper over `lazuli check` (doctor only)** — rejected: `verify` must report the FULL link chain (manifest→alias→contract→import→env) as an explicit per-plugin map an author/agent reads top-to-bottom, including the import-emission link doctor doesn't model. doctor owns the *contract* link as a gating diagnostic; `verify` owns the *whole graph* as a report. They share the contract logic but serve different surfaces.
- **Put the contract check only in `verify` (no doctor code)** — rejected: then a misdeclared adapter only fails if someone runs `verify`, not on `lazuli check` / CI / the LSP. The class fix requires the gating diagnostic; `verify` is the focused report that ALSO surfaces it.
- **Verify by parsing `adapter.go` for the `var _ Interface` line** (static Go scrape) — rejected as the PRIMARY mechanism: brittle (formatting/aliasing), and it proves the author *wrote* the assertion, not that it *holds*. We may surface its presence/absence as an advisory L3 detail, but the gating signal is the declared-contract + binding-graph check, and the real proof is `go build`.
- **Auto-discover bucket interfaces by scanning `runtime/go/lazuli/` at check time** — rejected for v1: the runtime tree may not be co-located with every pilot, and a hard-coded closed list (like `BUILT_IN_SEMANTIC`) is trustworthy and trivially testable. Growing the list is a deliberate, reviewed edit.

## Consequences
**We accept:** a hard-coded bucket-interface catalog that must be extended (one line) when a new runtime bucket ships — guarded by the fixture tests and consistent with the existing `BUILT_IN_SEMANTIC` precedent. A new CLI subcommand surface (`plugin verify`) and a new doctor code to register in three places (facets / module_headers header / run aggregator). `verify` reuses the resolver, so it inherits 0020's behaviour exactly (a feature, not a cost).
**We gain:** the "declared but silently inert" class dies in the adapter dimension — a misdeclared adapter fails at `lazuli check` time with a named fix; hostpoint (and every pilot) can answer "are my plugins actually wired?" with one command; an agent gets a machine-readable wiring map to self-correct; the static/runtime split is documented so no one mistakes `verify` PASS for a method-set guarantee.
**We watch:** if L3 ever FAILs a legitimately-bound adapter, the binding-detection (how we read the app's registry binding for a capability) is too narrow — widen the binding reader, never silence the link. If a new bucket interface ships and authors hit a false "unknown interface" FAIL, the catalog edit was forgotten — the fixture test that pins the known set is the reminder. And if a third surface ever needs the contract logic, it MUST call the shared contract-check function, not re-derive the bucket list.
