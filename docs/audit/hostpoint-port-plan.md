## Current Hostpoint architecture (source side)

### Authoring layer

Hostpoint today is generated by **Orion Studio** (the lead's prior framework attempt, the explicit negative reference for Lazuli per `docs/architecture.md:13-55`). Two Orion templates produce the codebase:

- `clean-arch-axum` — Rust/Axum backend.
- `expo-mvvm` — Expo (React Native) app.

Both targets carry `aerocoding-manifest.json` files inventorying every emitted file with hash + mtime + scope. Edits to `apps/hostpoint-app/` or `backend/hostpoint-api/` are technically possible but regen-overwrites the file unless manifest scope is set to `manual`. **The port to Lazuli replaces this generator pair.**

### Per-BC Rust crate shape (uniform across all 10)

```
crates/modules/<bc>/src/
├── domain/                aggregates + entities + VOs + events + validation
├── dto.rs                 boundary DTOs (serde + utoipa::ToSchema)
├── errors.rs              <Bc>Error enum (thiserror → axum::IntoResponse)
├── handlers.rs            axum routes
├── inbox.rs               idempotent consumer for cross-BC inbound messages
├── lib.rs                 crate root
├── reactions.rs           outbox event handlers (this BC emits → others react)
├── repository.rs          trait (port) + sqlx Postgres impl (adapter)
└── use_cases.rs           application services
```

`inbox.rs` + `reactions.rs` per crate = **transactional outbox + idempotent inbox** for cross-BC reliable messaging. This is a documented Orion pattern; Lazuli maps it to `event_group` / `event` / `emits` + `trigger event` jobs with `idempotency by envelope.id`.

### Firebase legacy surface

`firebase.json`, `firestore.rules`, `firestore.indexes.json`, `cloudstorage.rules`, plus `functions/src/` (https/services/triggers/utils). This is the **legacy BaaS layer being migrated out**. The Lazuli port absorbs:

- **Firebase Auth → Lazuli auth** (identity BC; Phase 1 fixture proves this works).
- **Firestore data → Postgres via pgx** (atlas-driven migrations).
- **Firebase Storage → `@plugin/<object-store>`** (TBD; see Decision D3).
- **Cloud Functions triggers → Lazuli `trigger event` jobs + `webhook` blocks**.
- **Cloud Functions HTTPS → Lazuli `api` blocks or `expose http` agents**.

The migration is therefore **two architectural rewrites stacked**: (a) Orion-generated Rust → Lazuli-generated Go, and (b) Firebase BaaS → Postgres-only with runtime services.

## Frontend topology decision: `hostpoint-app` + `hostpoint-os`

Hostpoint plans at least two frontends consuming the same backend:

- **`hostpoint-app`** — Expo (mobile-first; React Native). Currently `apps/hostpoint-app/`.
- **`hostpoint-os`** — web (admin/console/marketing). Confirmed via `c:/Users/lucas/dev/orion/.orion/export-hostpoint-os-manifest.mts` (exporter script for an Orion manifest specifically for hostpoint-os). Not yet present in the filesystem.

### Recommended shape (per `docs/invariants.md:578-587` + scope-discipline)

**One Lazurite capsule, multiple frontends declared in `Lazurite.toml`:**

```toml
[lazuli]
version = "0.x"

[lazurite]
template = "default"

[frontends.app]
target = "expo"
out = "dist/ts-app"
audiences = ["traveler", "host"]      # mobile audiences only

[frontends.os]
target = "next"                        # or "tanstack-vite" — see Decision D2
out = "dist/ts-os"
audiences = ["admin", "operator"]      # back-office audiences

# Other frontends future-proofed:
# [frontends.website]
# target = "next"
# audiences = ["marketing"]
```

In `.lzx` files, declare `audience traveler`, `audience host`, `audience admin`, `audience operator`. Each command/query inherits visibility per audience; per-frontend SDK only contains the surface its audiences can call (`AUDIENCE-NO-FRONTEND-001` / `FRONTEND-AUDIENCE-UNKNOWN-001` doctor rules enforce).

**Single capsule rationale:**

- One `app.lzi` = one backend binary (`dist/go/main.go`) = one Postgres = one feature graph. Inter-feature `uses` works across all BCs cleanly. River jobs and event subscriptions resolve within a single IR graph.
- Multiple frontends consume different audience-scoped SDKs from `dist/ts-<name>/`. This is the canonical Lazurite multi-frontend pattern; no special handling needed.
- Avoids cross-capsule plugin-shared-core hack that would otherwise be required for a microservice-style split.

**Where the user's question lands:** "hostpoint-os com back apontando tambem pro hostpoint-app e outras features" → in Lazuli terms, hostpoint-os is just another frontend declared in `[frontends.os]`. Its TS SDK can call the same backend routes that hostpoint-app can, restricted only by audience. The backend doesn't know which frontend is calling — only the actor's policy applies.

### When to NOT use single capsule

Only split into multiple capsules if **two backends would diverge** — e.g., a side product line ("Hostpoint Insights" mentioned in Orion's exec plan as a future spinoff) wants its own DB and feature graph. Then it's a separate Lazurite capsule, sharing code through `@plugin/hostpoint-core`.

For the v0 port: **one capsule, two frontends**. Confirm via Decision D1 below.

Order optimizes for **earliest production-grade signal** and **smallest blast radius per ship**.

### Phase 1 — Identity + scaffolding (1-2 sessions)

- Wire `Lazurite.toml` with both frontends declared (D1 + D2).

- Run `lazuli generate go && go build` → green.

- File LAZ-5 (G1 tenant-column shim) — blocks production-ready auth.
- File G2 (`@key.tenant`) — required before storing OAuth provider tokens server-side.

### Phase 2 — Catalog + host + traveler (3-5 sessions)

- These three BCs are the supply/demand + listing inventory. Largest schema surface; will surface the **MONEY-1** semantic gap (catalog has prices) and the **OBJECT-STORE** gap (listings have photos).
- File MONEY-1 proposal in parallel with catalog port.
- File OBJECT-STORE plugin authoring task; build minimal `@plugin/object-store` against MinIO local + S3 prod.
- File `@plugin/scalars-br` authoring task (CPF, CNPJ, CEP for host onboarding).
- Hostpoint-os MVP starts here: admin views over catalog + hosts + travelers.

### Phase 3 — Operations + payments + messaging (3-5 sessions)

- Operations: booking/order lifecycle — exercises Lazuli `workflow` + lifecycle invariants heavily.
- Payments: requires `@plugin/mercadopago` authoring (separate cell). Money flows expose MONEY-1 + EVENT-OUTBOX gaps explicitly.
- Messaging: exercises `channel` (realtime bucket) for chat; may exercise notification digest.

### Phase 4 — Trust + intelligence + platform (2-3 sessions)

- Trust: reviews/ratings — straightforward CRUD + lifecycle.
- Intelligence: LLM surfaces — exercises Lazuli `agent` blocks. Pleiades v2 already proved this works.
- Platform: cross-cutting admin/config/observability — likely the smallest BC.

### Phase 5 — Firebase data migration + cutover (1-2 sessions)

- Author one-off `tools/firestore-to-postgres.mts` migrator (lives in private hostpoint repo).
- Migrate Firebase Storage assets to chosen object store.
- Dual-write window (functions/ writes both → eventually flip read traffic) OR hard cutover with maintenance window.
- Retire `functions/`, `firebase.json`, `firestore.rules`.

**Total estimate: 10-17 sessions.** Wide because Phase 2 + Phase 3 are where most novel framework pressure lands. Each phase is gated on the previous shipping green doctor + green Go build.

## What NOT to do (anti-patterns to avoid)

Drawn from CLAUDE.md operational rules + lessons from 2026-05-12:

1. **Do not absorb hostpoint-specific business rules into the framework.** Commission tables, plan tiers, role-transition policies, listing-approval workflows — all go in `@fn.*` handlers or hostpoint repo, never in `crates/lazuli_*` or `runtime/go/lazuli/`.
2. **Do not name plugins after hostpoint.** `@plugin/mercadopago` not `@plugin/hostpoint/payments` (retired 2026-05-11 per `project_plugin_namespace_policy`).
3. **Do not launch a parallel-codex batch on the port without grading the L0 design first.** Hostpoint port has 10 BCs; the temptation to fan out is large. Per `feedback_grade_before_commit`, every L0 proposal goes through `lazuli-language-architect` BEFORE Codex.
4. **Do not commit hostpoint-private content to the public Lazuli repo.** Audits like this one may name the product + BCs; they may NOT carry quoted business rules, schema details encoding pricing/policy, partner names, or strategic plan content.
5. **Do not write 587-LOC `http_mtls`-style files in `runtime/go/lazuli/`.** Wire-thin principle: external import + call. If LOC > 100 and no external import, rewrite or kill.
6. **Do not let hostpoint-os be a fully separate capsule.** The user's question implied that mental model; the canonical Lazurite answer is single capsule + multiple frontends. Splitting too early forks the feature graph and prevents `uses <other-bc>` resolution across boundaries.
