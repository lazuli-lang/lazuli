# SPEC-08 — Collapse the four test dialects to two: keep generated permits/forbids vs authored allows/denies; fold accepted-by/rejected-by into allows/denies with a typed subject; resolve the eval-forbids vs matrix-forbids collision by retiring eval forbids in favour of denies

**Breaking:** True | **Est. commits:** 9 | **Depends on:** none | **Parallel with:** SPEC specs that touch unrelated keyword families (e.g. query.* kinds, event.trace, encryption/secret_rotation) — disjoint registry scopes and parser dispatch arms, Any spec NOT touching Context::Tests / Context::Policy registry scopes, the .lzx experience/surface parsers, agent evals parser, or the TEST-*/eval doctor families, Caveat: any other spec that edits crates/lazuli_keywords/src/registry.rs, docs/keyword-reference.md, or editors/vscode/syntaxes/lazuli.tmLanguage.json must be SEQUENCED with this one (shared generated artifacts + shared registry file) — regenerate after both land, not in parallel, per the git-discipline 'sequential > parallel on shared worktree' rule

## Problem
Lazuli's test surface currently speaks FOUR distinct verb dialects, three of which carry no information the typed subject doesn't already carry, and one of which collides a verb across two unrelated semantics:

1. AUTHORED predicate/edge tests (`.lzi` command/rule/transition `tests` blocks) use `allows`/`denies`. Lowered in `crates/lazuli_analyzer/src/lifecycle/mod.rs:372-396` (`lower_test_line` → `AllowsFrom`/`DeniesFrom`/`AllowsAs`/`DeniesAs`/`AllowsFromAs`/`DeniesFromAs`); IR catalog `crates/lazuli_ir/src/nodes/test_and_policy.rs:73-100` (`TestAssertion::AllowsWhen`/`DeniesWhen`/`AllowsFrom`/...). LSP recognises them in `crates/lazuli_lsp/src/test_blocks.rs:135-157` (`is_valid_test_assertion`).

2. GENERATED command actor-matrix rows use `permits`/`forbids`. IR `TestAssertion::PolicyAllow{actors}`/`PolicyDeny{actors}` (`test_and_policy.rs:74-77`). LSP flags hand-authored `permits @`/`forbids @` in command tests as a generated-only smell (`test_blocks.rs:75-86`). This split is DELIBERATE and DEFENDED — `docs/invariants.md:589-594` ("Generated command actor-matrix tests use `permits` and `forbids`; authored predicate and transition tests use `allows` and `denies`") and `docs/canonical-semantics.md:1518-1520` ("`permits`/`forbids` always talk about authorization subjects, while `allows`/`denies` always talk about evaluated predicates"). KEEP THIS.

3. `.lzx` view-extensibility tests use a THIRD dialect: `accepted by <feature>`/`rejected by <feature>`. Parsed in `crates/lazuli_syntax/src/parser/lzx/experience/mod.rs:254-285`; AST `LzxViewTestAssertion::AcceptedBy`/`RejectedBy`; lowered in `crates/lazuli_analyzer/src/lzx.rs:391-402`; IR `ViewTestAssertion::AcceptedBy`/`RejectedBy` (`crates/lazuli_ir/src/nodes/experience/mod.rs:144-159`). `docs/grammar.lzx.md:254-261` itself notes "The `accepted by`/`rejected by` shape is distinct from `.lzi` `tests` (which uses `allows`/`denies`)." But the distinction lives ENTIRELY IN THE SUBJECT (`extension <feature>`), not the verb: an allowlist membership test is just an authored allow/deny over a typed extension subject. This is a fourth vocabulary for the SAME polarity (allow/deny) that authored `.lzi` tests already express — pure entropy with no added rejection power, exactly the redundancy `validates field/resource`→`validates` (design-decisions.md §10) and the reverted bare `query` form (design-decisions.md §6, commit 7e263cd) were collapsed to avoid.

4. EVAL assertions (`agent ... evals ... case`) use `requires`/`forbids`. Parsed in `crates/lazuli_syntax/src/parser/lzi/agent/evals.rs:160-169`; AST `AgentEvalKind::Requires`/`Forbids` (`crates/lazuli_syntax/src/ast/agent.rs:220-225`). This produces a HARD VERB COLLISION: `forbids` means "negative assertion" in evals (`evals.rs:163`) AND means "generated negative authorization row" in the actor-matrix (`PolicyDeny`, `test_blocks.rs:138`). Both register under the SAME `Context::Tests` scope in the keyword registry — `forbids` appears twice with conflicting hover text (`crates/lazuli_keywords/src/registry.rs:2565-2570` "Test: permission forbidden." vs the eval meaning) and again under `Context::Policy` (`registry.rs:2629-2634`). Worse, `requires` is triple-overloaded: eval clause (`evals.rs:162`), feature-dependency line (`registry.rs:1724-1728` `Context::FeatureHeader`), AND a tests-scope filter/predicate connector (`registry.rs:3407-3411`). The keyword-reference reflects the mess: `requires` and `forbids` each render under multiple scopes (`docs/keyword-reference.md:463,469`).

Net: an LLM authoring a test must disambiguate among `allows`/`denies`/`permits`/`forbids`/`accepted by`/`rejected by`/`requires` and remember that `forbids` means two different things and `requires` means three. That is high output entropy (more retries) for zero added static-rejection power on dialects 3 and 4.

## End state
TWO test dialects survive, split on the ONE axis that is genuinely load-bearing (generated-vs-authored), with every collision resolved:

A. GENERATED authorization rows keep `permits`/`forbids` (command actor-matrix only). Unchanged. `docs/invariants.md:589-594` and `docs/canonical-semantics.md:1518-1520` continue to defend this as the at-a-glance "this row is machine-derived from `policy @policy.*`" signal. The `forbids` keyword is now UNAMBIGUOUS: it exists ONLY as a generated actor-matrix verb (under `Context::Tests`) and as a policy verb (under `Context::Policy`) — never again as an eval verb.

B. AUTHORED assertions everywhere use `allows`/`denies`, with the semantic dimension carried by the TYPED SUBJECT after the verb, never by a new verb:
   - `.lzi` predicate: `allows when <pred>` / `denies when <pred>` (unchanged).
   - `.lzi` transition edge/actor: `allows from <state>` / `denies as @role.x` / `allows from <state> as @role.x` (unchanged).
   - `.lzx` view extensibility (FOLDED): `allows extension <feature>` / `denies extension <feature>` REPLACES `accepted by <feature>` / `rejected by <feature>`. The subject `extension <feature>` is the typed discriminator — same pattern as `validates @validator.<name>` encoding scope in the type (design-decisions.md §10). `extension` enters the closed subject-keyword catalog for the Tests scope.
   - EVAL assertions (FOLDED): `requires <pred>` → `allows <pred>` and `forbids <pred>` → `denies <pred>`. Eval polarity is exactly authored allow/deny over the agent-output predicate subject; the eval-specific predicate extensions (`<ref> contains "..."`, `contains @semantic.X`, `tools.calls includes/excludes`) remain admissible only inside `evals` (unchanged — `docs/grammar.lzi.md:1128-1133`). This RETIRES `requires` and `forbids` as eval verbs, eliminating the `forbids` cross-semantic collision and removing one of the three `requires` overloads (the feature-dependency `requires` at `registry.rs:1724` and the `requires`-as-precondition connector survive untouched in their own scopes).

C. The eval `golden`/`min_score`/`case` block scaffolding is unchanged; only the assertion verbs inside a `case` move from `requires`/`forbids` to `allows`/`denies`.

D. `accepted`, `rejected`, and the eval `requires`/`forbids` spellings hard-error after migration: parser emits `E-TEST-ACCEPTED-BY-RETIRED` / `E-TEST-REJECTED-BY-RETIRED` / `E-EVAL-REQUIRES-RETIRED` / `E-EVAL-FORBIDS-RETIRED` (mirroring the existing `E-ATTACH-CTX-RETIRED`/`E-CONTEXT-RETIRED` precedent in CLAUDE.md). Registry drops the `accepted`/`rejected` Tests entries and adds `extension` as a Tests subject keyword.

After this spec the canonical answer to "how do I write a test?" is: `permits`/`forbids` ONLY for generated actor-matrix rows you almost never hand-write; `allows`/`denies` for everything you author, with `when`/`from`/`as`/`extension`/(bare-eval-predicate) naming the dimension. Two verbs, one canonical form per intent.

## Justification (token / entropy)
"TOKEN/ENTROPY (LLM-first metric = tokens-per-attempt × attempts):\n\nPEAKEDNESS (drives attempts↓). Today the test surface has FOUR allow/deny-polarity dialects (`allows`/`denies`, `permits`/`forbids`, `accepted by`/`rejected by`, `requires`/`forbids`) plus a `forbids` that means two different things and a `requires` that means three (registry.rs:1724, 2565, 3407; evals.rs:162-163; test_blocks.rs:138). An LLM sampling a test verb faces a 4-way (often 7-token) choice where 2 of the choices are ambiguous — high output entropy → more wrong first attempts → more retries. Folding to TWO dialects on the single load-bearing axis (generated permits/forbids vs authored allows/denies) yields ONE canonical form per intent: authored → always `allows`/`denies`, dimension named by the subject (`when`/`from`/`as`/`extension`/bare-eval-predicate); generated → always `permits`/`forbids`. The model no longer chooses a VERB to express extensibility or eval polarity; it reuses the allow/deny verb it already knows and varies only the subject — which it must emit anyway. Sharply peaked distribution → fewer attempts. This is the same entropy win the codebase already banked twice: reverting bare `query` (design-decisions §6) and unifying `validates field/resource` → `validates` (design-decisions §10), both citing cold-read clarity / no-information-in-the-keyword.\n\nTOKENS-PER-ATTEMPT (drives cost↓). The folded forms are tokenizer-cheap English: `allows extension checkout` and `denies output contains @semantic.Email` are bare-PascalCase/English-keyword surfaces under cl100k/o200k, identical in cost to the verbs they replace, and `extension`/`output` are single common tokens. No `@sigil.Type` is introduced. Retiring the `forbids`/`requires` overloads also removes hover/disambiguation context the model would otherwise spend tokens reasoning about.\n\nWHY NOT collapse ALL THE WAY to one dialect: keeping `permits`/`forbids` distinct is NOT entropy — it is a 1-bit at-a-glance signal ('this row is machine-generated from policy, do not hand-edit') that is statically enforced (test_blocks.rs:75-86) and explicitly defended (invariants.md:589-594, canonical-semantics.md:1518-1520). Collapsing it would FORCE the model to hand-author actor-matrix rows it should never write, raising error rate. So the optimum is exactly two dialects, split on generated-vs-authored — the one axis where the distinction carries information the subject cannot. The other three folds remove pure entropy; this one keep removes a contradiction surface (the doctor would otherwise need an extra rule to reconcile two meanings of `forbids`, per the recurring 'contradiction surface doctor must reconcile' anti-pattern in design-decisions Cut-A/A.11)."
