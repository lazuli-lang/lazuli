# SPEC-09 — Unify collection declarations — retire `field: many Type`, canonicalize on `has_many`

**Breaking:** True | **Est. commits:** 5 | **Depends on:** none | **Parallel with:** SPEC-08 (any non-overlapping keyword retirement that touches different registry entries) — coordinate only on the single shared regen step (xtask gen-tmlanguage / gen-keyword-reference) and the keyword_surface_parity gate; sequence the regen if two specs land in the same window to avoid a generated-file merge race, Any SPEC that edits a different feature/block surface (commands, queries, agents) — this spec is confined to the resource-body collection grammar

## Problem
Two collection-declaration forms coexist with inverted word order and divergent capability, and one of them is a half-dead trap. (1) `has_many <name>: <Type> [inverse <field>]` is the full form: dedicated parser at `crates/lazuli_syntax/src/parser/lzi/resource/has_many.rs` (with optional `inverse` at lines 43-50), registry statement keyword at `crates/lazuli_keywords/src/registry.rs:1823-1828`, lowered to typed `ResourceHasMany` (asserted in `crates/lazuli_syntax/src/parser/lzi/resource/mod.rs:453-456`). It carries the inverse FK column codegen needs. (2) `field: many Type` (e.g. `labels: many Label` at `examples/linear-issue.lzi:42`; documented `docs/canonical-semantics.md:359,385`) has NO dedicated parser. The resource dispatcher at `crates/lazuli_syntax/src/parser/lzi/resource/mod.rs:260-272` routes ANY `<name>: <Type>` line that doesn't match a body-handler prefix into `parse_resource_field_decl`, so `labels: many Label` is captured as a plain FIELD whose `type_text` is the literal string `"many Label"`. The type lifter `type_ref_from_syntax` (`crates/lazuli_analyzer/src/types.rs:53-73`) strips `list `/`list of `/`List ` into `TypeRef::Many(..)` but has NO `many ` branch — so `"many Label"` is reduced by `first_paren_balanced_token` (`types.rs:81`) to the first token `"many"`, lowering to `TypeRef::UserDefined("many")`. The relation silently vanishes: no `Many`, no inverse, no join table. The `many` type-constructor registry entry (`registry.rs:3123-3132`), its tmLanguage highlight (`editors/vscode/syntaxes/lazuli.tmLanguage.json:2702`), and its keyword-reference row (`docs/keyword-reference.md:837`) advertise a form that does not reach codegen, while it is absent from the LSP completion/hover catalog entirely — a parity gap. The grammar presents both as peers (`docs/grammar.lzi.md:334-337`), and `docs/design-decisions.md` has NO entry defending the dual form (it only ratifies `has_many` as cut-4 at line 509), so this is unjustified inverted-word-order friction, not a deliberate distinction. Two spellings for one intent = output entropy; one spelling that doesn't lower = a correctness trap. Only one in-repo use site exists: `examples/linear-issue.lzi:42`.

## End state
Exactly one collection-declaration form: `has_many <name>: <Type> [inverse <field>]`. The simple no-payload many-to-many that `many` expressed becomes `has_many labels: Label` (inverse omitted — already supported by `has_many.rs:43-50`). The `many` type-constructor is removed from `lazuli_keywords::ALL`; tmLanguage and `keyword-reference.md` regenerate without it; LSP never offered it. The parser hard-errors any field whose type text begins with the bare token `many ` with `E-MANY-FIELD-RETIRED`, suggesting the `has_many` rewrite — mirroring the `E-CONTEXT-RETIRED`/`E-WORKFLOW-RETIRED` precedent (`crates/lazuli_lsp/tests/keyword_surface_parity.rs:62-65`). `docs/grammar.lzi.md` drops `many_decl` (line 337); `docs/canonical-semantics.md:355-385` rewrites the `labels: many Label` worked example to `has_many labels: Label`; `examples/linear-issue.lzi:42` is migrated. A `RESOURCE-MANY-FIELD-RETIRED-001` doctor rule (iron-hand, error) is the whole-project scan surface that catches the retired form in any file the parse-time guard doesn't reach first (e.g. partial inputs, doctor-only flows), and a `lazuli upgrade` recipe rewrites `<name>: many <Type>` → `has_many <name>: <Type>` for existing pilots. After the change `inspect`/`generate --check` on the migrated example shows a real `ResourceHasMany`/`TypeRef::Many` relation where before there was a dead `UserDefined("many")` field.

## Justification (token / entropy)
"LLM-first metric = expected tokens to correct output = tokens-per-attempt × attempts. PEAKEDNESS (attempts↓): today two inverted-word-order spellings encode one intent — `has_many notes: CustomerNote` (verb-first) vs `notes: many CustomerNote` (noun-first). A model sampling the collection construct splits probability mass across both orders, and worse, one order (`many`) lowers to a BROKEN UserDefined(\"many\") field (types.rs:81), so a fraction of 'correct-looking' generations are silently wrong — the model gets no compile-time signal and the retry loop never terminates on first attempt. Collapsing to a single verb-first form `has_many <name>: <Type>` makes the construct unimodal: one canonical token order, output entropy drops, and the parser hard-error on the retired spelling converts the silent-correctness trap into an immediate, self-correcting diagnostic (one extra attempt that names the fix, vs unbounded silent failure). TOKENS-PER-ATTEMPT (cost↓ or neutral): `has_many labels: Label` and `labels: many Label` are within a token of each other under cl100k/o200k (both bare English keywords + PascalCase type, no @sigil), so peakedness is the dominant lever here, not surface cost — and we keep the cheap bare-PascalCase `Label` rather than any sigil form. The verb-first `has_many` also front-loads the relation semantics (the reader/model knows it's a collection before reaching the type), which improves cold-read parse-ahead. Net: strictly fewer attempts, equal tokens-per-attempt, and elimination of a class of unrecoverable silent error — a clean reduction in expected tokens to correct output. The cut is also the smallest possible (one registry entry removed, one guard added, one example migrated), so it imports no new vocabulary an LLM must learn."
